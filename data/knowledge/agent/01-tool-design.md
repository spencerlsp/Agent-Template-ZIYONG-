# 工具设计原则

工具是 agent 唯一能改变世界的手段，设计得好坏直接决定它能不能解决问题。

## 一个工具只做一件事

把"读文件"和"改文件"分成两个工具，而不是合成一个带 mode 参数的。
模型的参数填错概率远高于选错工具，参数越少越不容易出错。

## 描述比 schema 重要

Schema 只告诉模型"要什么参数"，描述才告诉它"什么时候该用、结果是什么"。
描述里应当写清触发场景，而不是复述实现。实测中同一套 schema、
不同措辞的描述，会让调用成功率差出很多。

## 参数要能自我校验

用类型注解声明参数，让框架自动校验。模型可能给出字符串形式的数字、
漏掉必填项、或者多塞一个不存在的字段，这些都要在进入业务逻辑之前挡住。

## 错误要返回文本而不是抛异常

抛出异常会中断整个循环，用户看到的是程序出错；返回错误文本则让模型看到问题所在，
它有机会换个参数重试。这条在实践中很有效：时区名写错、路径不存在，
模型看一眼错误就知道该怎么改。

## 权限边界在自己的代码里

模型是不受信任的输入源。文件路径要在沙箱根目录内解析并校验，
数据库工具要限制成只读并限制可访问的表。**环境由你在注册时冻结，
参数才交给模型**——绝不能让模型自己指定根目录。
