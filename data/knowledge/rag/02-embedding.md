# Embedding 模型的选型

Embedding 决定"语义相近"能被多大程度识别出来，是 RAG 质量的第二个上限。

## 维度不是越高越好

常见维度有 384、768、1024、1536。维度高表达能力强，但存储和计算成本成正比增长。
对于几百到几千份文档的规模，1024 维已经足够，再往上收益递减。

## 多语言与中文

选模型时先看它在中文上的表现。BGE 系列和 M3E 系列对中文支持较好；
`BAAI/bge-m3` 是多语言模型，中英混排的语料不用分别处理。

## 离线兜底实现

开发和测试阶段可以先用**哈希向量**：不做语义理解，只把词袋压成定长向量。
它给出的召回质量一般，但胜在零依赖、零成本、结果确定，能让整条链路在没有 API Key
的情况下跑通并接受测试。上线前再换成真实模型。

## 换模型必须重建索引

这是最隐蔽的坑：索引里存的是旧模型生成的向量，查询用的是新模型，两者不在同一个
向量空间里，检索结果会静默地全错——不报错、不崩溃，只是答案变得毫无关系。

因此索引里应当记录 embedder 的名字和维度，启动时比对，不一致就要求重建。

## 批量与并发

调用远端 embedding 接口时按批发送，每批三十二条左右比较稳妥。串行分批在文档量大时
会很慢，改成并发若干批可以显著缩短建库时间。
