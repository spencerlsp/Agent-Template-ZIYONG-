# evals —— 检索评测与延迟基准

> 这一层回答两个问题：答案**有没有被检索回来**（准不准），以及**要等多久**（快不快）。

## 负责什么

| 它管 | 它不管 |
| --- | --- |
| 数据集格式与锚点自检 | 答案质量（幻觉率、引用准不准），那要 LLM 裁判 |
| 三个检索指标：Recall / HitRate / MRR | 生成阶段的失败（模型拿着正确片段答错，不记在检索头上） |
| 三路对比：纯向量 / 纯关键词 / 融合 | 端到端响应时间（含模型生成），那是另一层 |
| 延迟基准：分位数统计（[`bench_search.py`](bench_search.py)） | 显存、吞吐、并发这类容量指标 |

两个脚本分工明确，建议不要合并：

- [`run_eval.py`](run_eval.py) —— **准不准**。要的是可复现，所以一次一条、跑一遍。
- [`bench_search.py`](bench_search.py) —— **快不快**。要的是稳定，所以每条重复多次取分位数。

## 为什么先只评检索，不评生成

检索指标便宜、稳定、可复现——只用到 embedding 和 BM25，60 条问题几秒跑完。
而"答案质量"要引入 LLM 裁判，成本和噪声都高一个量级：裁判模型自己会飘，同一份
答案跑两次可能得到不同结论。

更实际的原因是**归因**：模型答错有两种可能，检索没把正确答案捞回来，或者捞回来了
但它看漏了。先用检索指标把第一种情况排掉，剩下的才值得去查提示词。

所以顺序是：**先把检索的尺子做准，再谈生成。**

## 数据集：`dataset.jsonl`

JSONL 格式，一行一个用例（允许空行和 `#` 注释——这是我们自己的约定，JSONL 本身不支持）：

```json
{"id":"hy-01","query":"错误码一类的字符串为什么向量检索不行","gold":[{"source":"rag/03-hybrid-retrieval.md","contains":"对精确匹配很弱"}],"kind":"术语精确"}
```

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| `id` | 是 | 用例标识，出现在逐条结果里 |
| `query` | 是 | 用户会怎么问。**写口语，别抄原文** |
| `gold` | 是 | 标准答案的位置列表，可以多条 |
| `kind` | 否 | 问题类型（`术语精确` / `语义改写` / `多跳` / `结构定位` / `陷阱`），用于分桶统计 |
| `note` | 否 | 给你自己看的备注 |

`gold` 的每一项：

| 字段 | 含义 |
| --- | --- |
| `source` | 源文档的相对路径（相对 `data/knowledge/`） |
| `contains` | 答案所在的那句话里的**一小段原文**（十几个字即可） |
| `occurrence` | 同一句话在文档里出现多次时，指的是第几次（默认 1） |

### 为什么锚"关键句"而不是行号或字符偏移

锚行号的话，文档改一个字，所有锚点就全错了；锚关键句则只要求这句话还在。
更重要的原因见判定规则一节：**这个判定对切块参数完全免疫**——片段切大切小、
带不带标题前缀，都不影响"这句话是否出现在片段里"。

### 数据集自检：先证明尺子没坏

`run_eval.py` 在开始评测前会跑一遍 `validate()`：把每条 `gold.contains` 拿到
源文档里去找，找不到就直接报错退出，**不给分数**。

这一步比指标本身还重要。如果 `contains` 打错一个字，或者文档后来改过，这条用例
会永远算"未命中"，而你会以为是检索系统不行——**数字被污染了却看不出来**。
所以宁可让脚本在开头就崩。

## 判定规则：什么算"命中"

只看检索结果的前 k 条（`--top-k`，默认 5）。一条 `gold` 命中，当且仅当存在某个片段：

```
片段的 source == gold.source  且  gold.contains 是片段文本的子串
```

**来源必须比对。** 同一句"检索结果必须带出处"可能出现在两篇文档里，只比文本会把
来自错误文档的片段也算成命中，指标会凭空变好。

**这个判定偏悲观。** 如果一句话正好被切在两个片段中间，两边都不含完整句子，
会算作未命中。但这类失败恰恰是最该暴露的（说明切块切得不好），所以宁可偏悲观。

## 三个指标的公式

记号：一次评测有 `C` 条用例，第 `i` 条用例有 `g_i` 条标准答案（本数据集里 `g_i` 恒为 1，
但公式按通用情况写），前 k 条检索结果记为 `R_i(1..k)`。

### Recall@k（召回率）

```
                     所有用例命中的标准答案总数
Recall@k = ─────────────────────────────────────────
                       所有标准答案总数

              Σ_i  hit_i                 hit_i = 第 i 条用例命中的 gold 条数
          = ─────────────
               Σ_i  g_i
```

它回答的是"**该被捡回来的东西，捡回来了多少**"。这是天花板指标：**Recall 不到 1，
后面的指标全都无从谈起**——模型的生成能力再强，也变不出一个根本没检索到的片段。

举例：60 条用例各有 1 条标准答案，其中 57 条命中，则 `Recall@5 = 57/60 = 0.950`。

### HitRate@k（命中率）

```
                   至少命中 1 条标准答案的用例数
HitRate@k = ──────────────────────────────────────
                            用例总数

                |{ i : hit_i > 0 }|
          = ────────────────────────
                        C
```

它回答的是"**有多少问题完全没希望**"。和 Recall 的区别在于：一条用例若有 3 条标准
答案、只命中 1 条，Recall 记 1/3，HitRate 记满分。

两者的关系：**每条用例的标准答案数量相同时（本数据集 `g_i` 恒为 1），HitRate ≥ Recall**。
证明很简单：`Σ hit_i ≤ g · #{i : hit_i > 0}`，两边同除 `C·g` 就得到 `Recall ≤ HitRate`。
在本数据集里两个数字恰好相等——**换成多标准答案、且各用例标准答案数量不一样的用例
（比如"列出三种失败模式"），它们就会分叉，而且大小关系不再固定**，那时两个都要看。

### MRR（Mean Reciprocal Rank，平均倒数排名）

先算单条用例的倒数排名 `RR`，再对所有用例取平均：

```
        ⎧ 1 / r_i     第 i 条用例首个命中排在第 r_i 位
RR_i =  ⎨
        ⎩ 0           一条都没命中

         1     C                         r_i ∈ {1, 2, ..., k}
MRR = ──── ·  Σ  RR_i
         C    i=1
```

它回答的是"**命中了，但排得够靠前吗**"。位次 1 得 1 分、位次 2 得 0.5 分、
位次 3 得 0.33 分——因为片段越靠前，模型越可能重点参考，被上下文窗口挤掉的风险也越小。

举例：三条用例的首个命中排名分别是 1、1、3，则
`MRR = (1 + 1 + 0.333) / 3 = 0.778`。

**MRR 是重排（rerank）唯一能改善的指标**：重排不改变候选集合、不新增也不删除片段，
只调整顺序，所以 Recall 一动不动，MRR 会涨。这也是判断"该不该上重排"的信号：
**Recall 已经很高、MRR 却偏低，说明候选都在池子里，只是排得不对。**

### 三个指标怎么配合看

| 你看到 | 说明什么 | 下一步做什么 |
| --- | --- | --- |
| Recall 低 | 召回问题：正确答案压根没进候选池 | 换更强的 embedding、调切块参数、开查询改写 |
| Recall 高、MRR 低 | 排序问题：候选里有正确答案，但压在第 3、4 位 | 上重排 |
| 两个都高、答案还是错 | 不是检索的问题 | 查提示词、查模型能力、查片段是否被截断 |
| HitRate 远低于 Recall | 每条用例有多个标准答案，只捞到一部分 | 看是不是同一主题分散在多个章节 |

### 顺带说明：检索阶段用到的那些分数

评测不关心检索内部用什么分数，但调试时会看到它们，别混淆：

- **向量路**：查询向量与片段向量的点积（向量已归一化时等于余弦相似度）。
- **关键词路**：BM25 分数，由 TF、DF/IDF 和文档长度归一化组成。
- **融合**：RRF 分数 `Σ 1/(60 + 名次)`，**只有名次含义，绝对值无意义**。
- **重排**：cross-encoder 给出的 `relevance_score`（0~1，每条 query 各自一套标定）。

BM25 的 TF / DF / IDF 完整公式、RRF 的来历、重排分数的语义，见
[rag/README.md](../src/agent_template/rag/README.md) 的"分数的公式"一节。
这四个分数**没有一个该塞进提示词给模型看**，原因也在那里。

## 三路对比

同一批用例跑三遍，唯一的变量是走哪路检索：

| 模式 | 怎么算的 | 用来回答 |
| --- | --- | --- |
| 纯向量 | 只取 `_vector_ranking()` 的前 k | embedding 的语义能力够不够 |
| 纯关键词 | 只取 `_keyword_ranking()` 的前 k | 字面匹配能救回多少 |
| 融合 | 走正常的 `search()`，即 RRF 融合（开重排时还会过一遍重排） | 生产环境实际的表现 |

融合列的名字会随配置变化（`融合(RRF)` 或 `融合(RRF+重排)`）——报告里必须写清是哪一版，
否则读者会拿"纯 RRF 的数字"去和"开了重排的数字"对比。

另外还会打印**独家命中**：只有向量路命中 / 只有关键词路命中 / 两路都没命中。
三路指标只是平均值，这份名单才是"混合检索到底有没有用"的直接证据——两路各有独家命中，
融合才有意义；一切都被一路包圆，另一路就是白跑的。

## 实测基线

60 条用例 / 19 篇文档 / 100 个片段 / `BAAI/bge-m3` / `top-k=5`：

| 模式 | Recall@5 | HitRate@5 | MRR |
| --- | ---: | ---: | ---: |
| 纯向量 | 0.933 | 0.933 | 0.758 |
| 纯关键词 | 0.917 | 0.917 | 0.782 |
| 融合(RRF) | 1.000 | 1.000 | 0.792 |
| 融合(RRF+重排) | 1.000 | 1.000 | **0.936** |

读法：Recall 在融合之后就到了 1.000，说明**候选池里从来不缺正确答案**，缺的只是排序；
重排把 MRR 从 0.792 抬到 0.936，代价见下节。

MRR 是个"倒数排名"的平均，不好直接读出"排第几"。假设命中都落在前两名（实测基本如此），
`MRR = (x·1 + y·0.5) / 60`：重排前约 **35 条排第 1、25 条排第 2**；重排后变成
约 **52 条排第 1、8 条排第 2**。这批用例的问题从来不是"找不到"，而是"排第二"。

顺带一个重要的结论：**这份数据集已经被打满了**。再往上调检索（换更大的 rerank 模型、
加候选数）收益极小，真正该做的是加难用例——跨文档的多跳问题、口语化改写、带指代的追问。
指标饱和的评测集比没有评测集更危险，因为它会给你"已经很好了"的错觉。

## 怎么用

```bash
# 建索引（评测要读它）
uv run agent index

# 跑评测：默认 top-5，三路对比 + 类型拆分 + 独家命中
uv run python evals/run_eval.py

# 看逐条结果（哪条用例挂了、挂在哪一路）
uv run python evals/run_eval.py --verbose

# 换个 k 看敏感度：k 越小越能暴露排序问题
uv run python evals/run_eval.py --top-k 3

# 把结果写成 evals/report.md，提交进 Git 对比不同版本
uv run python evals/run_eval.py --write-report
```

改检索策略时的标准流程是：**先跑基线 → 改一处 → 再跑 → 对比同一张表的同一列**。
一次只改一处，否则数字动了你也不知道是谁的功劳。

## 延迟基准：`bench_search.py`

准不准之外，第二个问题是快不快。两个脚本分开的原因在开头说了：这个要重复采样。

```bash
# 基线：不重排
AGENT_RERANK_PROVIDER=none uv run python evals/bench_search.py --repeat 3

# 开重排
AGENT_RERANK_PROVIDER=openai_compat uv run python evals/bench_search.py --repeat 3
```

它打印 mean / p50 / p90 / p95 / max 六个数字，以及**重排失败回退的次数**。

### 分位数是什么

把这轮所有计时结果升序排成 `x_1 ≤ x_2 ≤ ... ≤ x_n`，第 p 百分位的值按线性插值取：

```
h = (n - 1) · p / 100
分位数 = x_⌊h⌋ + (h - ⌊h⌋) · (x_⌈h⌉ - x_⌊h⌋)
```

| 名字 | 含义 | 怎么用 |
| --- | --- | --- |
| mean | 算术平均 | 参考用，**别拿它下结论** |
| p50 | 中位数：一半样本比它快 | 代表"典型情况下要等多久"，结论看这个 |
| p90 / p95 | 最慢的那 10% / 5% | 尾部延迟，用户抱怨的往往是这里 |
| max | 最慢的一次 | 基本是运气，样本少时别当结论 |

为什么不能只看 mean：假设 20 次里有 19 次 300ms、1 次 3000ms，`mean = 435ms`
——这个数既不代表典型（300ms），也不代表最坏（3000ms）。而 p50 告诉你"通常 300ms"，
p95 告诉你"每 20 次有 1 次 3 秒"。

### 怎么读两组数字

| 观察 | 含义 | 对策 |
| --- | --- | --- |
| p50 的差值 ≈ p95 的差值 | 代价是**固定的**每次开销（一次网络往返 + 打分） | 只能靠减少调用次数或换更快的服务 |
| p95 的差值远大于 p50 的差值 | 代价里含**抖动**（排队、偶发慢请求） | 加超时、加重试、加重排失败的降级 |
| 回退次数 > 0 | 量到的其实是"降级之后"的速度 | 先修重排，再重测 |

### 实测数字

60 条问题、每条重复 3 次（n=180），同一台机器、同一次会话内先后跑：

| 配置 | mean | p50 | p90 | p95 | max |
| --- | ---: | ---: | ---: | ---: | ---: |
| `none` | 130 ms | 108 ms | 158 ms | 341 ms | 528 ms |
| `openai_compat:BAAI/bge-reranker-v2-m3` | 435 ms | 405 ms | 559 ms | 650 ms | 758 ms |
| **差值** | **+305** | **+297** | **+401** | **+309** | +230 |

结论有三条值得抄进决策里：

1. **约 +300ms 是稳定成本，不是抖动**：差值在 p50、p95、mean 上几乎一样。所以不需要
   为它加特殊的容错，只需要知道"每次检索都多付 300ms"。
2. **一轮对话可能调用多次检索**。模型在一轮里连调两次 `search_knowledge_base` 是常态，
   那么这 300ms 就是 +600ms。评估代价时按"每轮调用几次检索"算总账。
3. **相对波动反而被摊平了**：基线 `p50 108 → p95 341` 是 3.2 倍，加了重排后
   `405 → 650` 只有 1.6 倍，因为一个大常量加在所有样本上。

### 跑基准时的四个坑

1. **先热身**。第一次检索要懒加载全库、建 BM25 索引、初始化 HTTP 连接池，那几百毫秒是
   启动成本。脚本默认 `--warmup 3`，热身的那几条不计入统计。
2. **别边跑边干别的**。下载、编译、看视频都会污染网络延迟，而延迟基准的全部意义就是
   这个数字。
3. **两组要用同样的 `--limit` 和 `--repeat`**。样本数不同，分位数不可比。
4. **两组都包含一次 embedding 的网络往返**（除非 embedding 也是离线的）。这是故意的：
   两组都付这笔钱，差值才干净地等于重排的代价。

## 后续可做（按性价比排序）

| 优先级 | 事项 | 说明 | 工作量 |
| --- | --- | --- | --- |
| 高 | **加难用例** | 当前 60 条已被打满（Recall 1.000），继续调参看不出差别。补三类题：跨文档多跳、口语化改写、带指代的追问。指标掉下来才说明尺子变准了 | 半天 |
| 高 | **基线回归保护** | 把当前数字钉进 CI：改检索代码后 Recall 掉 0.02 以上就失败。没有这条，优化全靠感觉 | 半天 |
| 中 | **失败归因自动分类** | 逐条失败目前靠人看。可以自动分成"切块切断""embedding 语义不匹配""关键词分词没覆盖"几类，直接指出该改哪一层 | 一天 |
| 中 | **生成质量评测（LLM 裁判）** | 检索对了不代表答案对。用一份固定提问 + 参考答案，让裁判模型按"引用是否准确、是否编造"打分，并保留裁判的原始理由以便复核 | 一到两天 |
| 低 | **基准的冷/热分离** | 现在只量热态（同一问题连测两次）。可以补一个"每条只测一次"的冷态模式，看缓存与连接池的作用 | 半天 |
| 低 | **多配置批量对比** | 现在切配置要跑两条命令。可以支持一次跑 `none / top10 / top20` 几组配置出一张表 | 半天 |
