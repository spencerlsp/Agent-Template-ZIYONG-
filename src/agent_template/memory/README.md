# memory —— 会话记忆

> 模型自己没有记忆，每次请求都要把历史重新发过去。这一层负责把历史存下来、
> 按会话隔离、并按规则裁剪。

## 负责什么

- **持久化**：把每条消息（含工具调用与结果）按会话存进 SQLite。
- **读取**：按会话读回历史，并做**安全裁剪**。
- **管理**：列出会话、统计条数、清空会话。

## 不负责什么

| 你可能会以为它管，但其实不管 | 实际在哪 |
| --- | --- |
| 系统提示 | 每轮由 `agent/prompts.py` 重新拼；**不入库**，因为它依赖当前的技能和工具 |
| 上下文压缩 / 摘要 | 目前没有，只有按条数裁剪（见"后续可做"） |
| 跨会话的长期记忆 | 没有。这里只做"一个会话内的对话历史" |
| 多用户隔离 | 用 `session_id` 区分，但没有身份校验 |

## 成员清单

| 名字 | 类型 | 职责 |
| --- | --- | --- |
| `MemoryStore` | 类 | 会话历史的全部操作入口 |
| `append()` | 方法 | 追加一条消息，同时把会话标记为活跃 |
| `history()` | 方法 | 读回历史（默认最近 40 条），**裁剪时会对齐到 `user` 消息边界** |
| `clear()` | 方法 | 清空某个会话，返回删除条数 |
| `sessions()` | 方法 | 列出所有会话及最后活跃时间 |
| `count()` | 方法 | 某个会话的消息条数 |
| `close()` | 方法 | 关闭数据库连接 |

数据库两张表：`messages`（一条消息一行，内容是我们自己的 `Message` 的 JSON）
与 `sessions`（会话活跃时间）。

## 类之间的关系

```
   agent/loop.py                    cli.py
        │                              │
        │ history() / append()         │ sessions() / clear()
        ▼                              ▼
                MemoryStore
                     │
                     ▼
           .agent/memory.sqlite3
                messages(session_id, role, payload, created_at)
                sessions(session_id, updated_at)
```

`AgentLoop` 是唯一会 `append()` 的地方：用户消息、模型的每条回复（包括只有
`tool_calls` 的那种）、每个工具结果，都要按顺序落库——**因为它们之间的顺序
本身就是协议的一部分**。

## 为什么这么设计

**1. 为什么存我们自己的 `Message`，而不是供应商的原始格式。**
换模型供应商时，历史不需要迁移。这也意味着历史是可读的、可被别的消费者解析的
（比如将来做 Web 前端，可以直接把历史渲染出来）。

**2. 为什么裁剪必须对齐到 `user` 消息边界（这个坑很隐蔽）。**
`assistant` 的 `tool_calls` 消息和紧随其后的 `tool` 结果消息是**一对**。
如果按条数硬截（比如"只保留最近 40 条"），很可能把一对从中间劈开。后果是下一次
请求被接口拒绝，报错信息通常长这样：

```
400 - messages with role 'tool' must be a response to a preceding message with 'tool_calls'
```

看到这个错误很难联想到是**裁剪**造成的。所以 `history()` 在取够条数之后，
会把窗口的开头往前推进到最近的一条 `user` 消息。

**3. 为什么系统提示不入库。**
它每轮重建，因为技能目录和工具清单会变（加载了新的 MCP server、改了技能文件）。
如果把某一版系统提示存进历史，下次就会带着过期的工具清单去请求——模型会调用
一个已经不存在的能力。

**4. 为什么顺序是"先读历史、再追加本轮输入"。**
反过来的话，本轮的用户消息会既出现在历史里、又作为独立参数拼进去，**发两次**。
`AgentLoop.run()` 里那三行的顺序是有意的：

```python
history = self.memory.history(session_id)   # 1. 先读（此时不含本轮）
self.memory.append(session_id, user_message)  # 2. 再落库
messages = [system, *history, user_message]   # 3. 再拼本次请求
```

**5. 为什么默认只保留 40 条。**
token 成本和历史长度成正比，而多轮对话的历史会一路膨胀。40 条是个保守默认值：
够保持上下文连贯，又不至于让每轮请求都背着全部历史。要改就改 `history()` 的
`limit` 参数（目前没做成配置项，因为它的合适值高度依赖你的使用方式）。

## 怎么扩展

### 换个存储

`MemoryStore` 的接口就是 6 个方法。换成 Postgres / Redis / 文件，只要保持这些
方法的语义（尤其 `history()` 的裁剪规则），上层不用动。

### 加"清空但保留最近 N 条"

```python
def trim(self, session_id: str, keep: int = 10) -> int:
    """删除较早的消息，只保留最近 keep 条（同样要对齐 user 边界）。"""
```

### 导出会话

现在的 `payload` 就是 JSON，导出很简单——适合做"把一次排查过程分享给同事"这类功能。

## 后续可做（按性价比排序）

| 优先级 | 事项 | 说明与建议 | 大致工作量 |
| --- | --- | --- | --- |
| 高 | **自动摘要压缩** | 长对话真正的解法不是"砍掉旧消息"，而是把早期历史压成一段摘要（用一次便宜的模型调用），保留"做了什么决定"这类要点。建议在 `history()` 里做：超过阈值就先摘要前一半 | 一天 |
| 中 | **token 预算而非条数** | 现在按"条数"裁剪，但 40 条短消息和 40 条长消息差别巨大。改成按 token 估算（用字符数近似即可）更合理 | 半天 |
| 中 | **会话命名与标签** | 现在只有 `session_id`。加一个 `title` 字段，`agent sessions` 里显示"这次会话在聊什么" | 两小时 |
| 中 | **导出 / 导入** | 方便分享排查过程，也方便做离线分析 | 两小时 |
| 低 | **长期记忆** | 把"值得记住的事实"（用户偏好、项目约定）向量化后跨会话检索。这是另一个量级的功能，会引入"记错了怎么办"的新问题，建议单独设计 | 三天起 |
| 低 | **多用户与权限** | 目前 `session_id` 由调用方自报，没有校验。做成服务时要加认证并把 session 绑定到用户 | 两天 |

我的建议：**先做"自动摘要压缩"**。它是多轮对话真正的瓶颈——不解决它，对话一旦
变长，要么砍历史导致前言不搭后语，要么带着全部历史导致成本和延迟一起涨。
