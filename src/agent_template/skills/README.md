# skills —— 技能层

> 把**人写的做事流程**交给模型，同时不把上下文撑爆。
> 技能是纯文本，不执行任何东西——模型读完流程，仍然要通过工具去行动。

## 负责什么

- **解析**：读取 `SKILL.md`，拆出 YAML 头部（`name` / `description`）与正文。
- **两级暴露**：系统提示里只放"目录"（名字 + 一句话），正文按需读取。
- **按需读取**：把正文包装成 `load_skill` 工具，模型需要时自己取。

## 不负责什么

| 你可能会以为它管，但其实不管 | 实际在哪 |
| --- | --- |
| 技能的版本、发布、来源管理 | 目前就是本地目录，没有版本概念 |
| 权限控制 | 技能是文本，没有权限可言；风险在它让模型去调的工具上 |
| 技能的执行 | 技能不执行任何代码，模型读完照样得调工具 |
| 技能被触发时的流程控制 | 由模型自主决定，这里只提供"读"的能力 |

## 成员清单

| 名字 | 类型 | 职责 |
| --- | --- | --- |
| `Skill` | dataclass | 一个技能：`name` / `description` / `body` / `path` / `metadata` |
| `Skill.render()` | 方法 | 拼出交给模型的完整文本（标题 + 描述 + 正文） |
| `parse_frontmatter()` | 函数 | 拆 `---` 包裹的 YAML 头与正文；解析失败时降级成"整个文件都是正文" |
| `load_skill_file()` | 函数 | 读单个文件，产出 `Skill`；读不了返回 `None`，不抛异常 |
| `first_line()` | 函数 | 没有 `description` 时的兜底：取正文第一行非标题文字 |
| `SkillsIndex` | 类 | 所有技能的集合，按名字寻址 |
| `SkillsIndex.catalog()` | 方法 | **给系统提示用的精简目录**（名字 + 描述） |
| `SkillsIndex.read()` | 方法 | 取正文；不存在时返回错误文本，交给模型自己纠正 |
| `register_skill_tools()` | 函数 | 注册 `load_skill` / `list_skills` 两个工具 |

## 类之间的关系

```
  skills/<名字>/SKILL.md
          │
          │ load_skill_file()  ← parse_frontmatter()
          ▼
       Skill ──► SkillsIndex ──┬── catalog() ──► 系统提示（只有名字 + 一句描述）
                               │
                               └── read()    ──► load_skill 工具（模型按需调用）
```

左边是"一次性成本"，右边是"按需成本"。这个分工就是这一层存在的全部理由。

## 为什么这么设计

**1. 为什么技能和工具要分开。**
工具是**原子能力**（读文件、算数、检索），技能是**流程**（这类任务该怎么做）。
把它们混在一起的后果是：要么把流程硬编码进工具的参数里，要么把能力写死在提示词里。
分开之后，能力可以复用，流程可以随时改——改技能只是改一个 markdown 文件，
不需要动代码、不需要重新部署。

**2. 为什么必须"渐进式披露"。**
一个写得好的技能往往有几百到几千字。如果全部塞进系统提示，每轮请求都要为它付
token，技能一多成本会失控。所以这里做了两级：

```
目录（进提示）：     - sql-review：审查 SQL 时的检查清单……
正文（按需读取）：    1. 先看索引…… 2. 再看 NULL 语义…… （几千字）
```

模型只在判断"这个任务匹配这个技能"时才调用 `load_skill`。代价是多一次工具调用，
换来的是**可以放几十个技能而几乎不增加固定成本**。

**3. 为什么用真 YAML 解析器，而不是自己写个 `key: value` 的循环。**
一开始确实是手写的，后来换成 PyYAML，因为真解析器支持折叠块：

```yaml
description: >-
  本项目默认的回答风格：结论先行，再给依据，最后补一个具体例子。
  没有更具体的技能适用时，用它。
```

多行描述不必挤成一行。这类"描述"字段恰恰是最需要多行的，因为**它直接决定模型
要不要加载这个技能**。

**4. 为什么缺 `name` / `description` 也要能加载。**
容忍不完美的输入：`name` 缺失时退回目录名，`description` 缺失时取正文第一行。
理由很实际——一个格式写错的技能不该让整个 agent 起不来。解析失败时记 warning，
降级处理，而不是抛异常。

**5. 技能的正文用什么语言写？**
都可以。模型会跟随语言：中文技能会让它用中文回答，英文同理。这一点值得记住，
因为**技能是少数几个"不需要改代码就能调整模型行为"的地方**。

## 怎么扩展

### 写一个好的技能

关键是 `description`——它是模型判断"要不要读这个技能"的唯一依据：

```markdown
---
name: sql-review
description: 审查 SQL 时的检查清单。当用户要求 review SQL、排查慢查询、或问"这个索引该不该建"时使用。
---

# SQL 审查清单

按顺序检查，发现问题就停下来说明，不要一次性列完所有可能：

1. **索引**：WHERE / JOIN / ORDER BY 的字段上有没有合适的索引？
2. **NULL 语义**：`NOT IN` 遇到 NULL 会返回空集，确认用户是否意识到这点。
3. **锁范围**：这条 UPDATE 会锁多少行？有没有走全表扫描的风险？
4. **返回量**：有没有 LIMIT？会不会把百万行捞回应用层？
```

写法建议：

- `description` 里写**触发场景**（"当用户要求……时使用"），而不只是主题。
- 正文写成**可执行的步骤**，而不是知识科普——模型不缺知识，缺的是"在这个项目里该按什么顺序做"。
- 明确写出**不要做什么**（"不要一次性列完所有可能"），这往往比正面指令更有效。

### 让技能引用更多资料

技能正文里可以指向仓库里的其他文件：

```markdown
详细的字段命名规范见 `docs/naming.md`，需要时用 read_file 读取。
```

这构成第二级按需加载：**目录 → 技能正文 → 技能引用的文件**。层级越深，
固定成本越低，代价是模型需要多走一步。

### 从别处加载技能

`SkillsIndex.from_dir()` 只接受一个目录。要支持多来源（比如个人技能 + 团队技能），
合并即可：

```python
index = SkillsIndex.from_dir(repo_skills)      # 先读仓库内置的
for extra in user_skill_dirs:                   # 用户目录可覆盖同名技能
    index = SkillsIndex([*index.raw(), *SkillsIndex.from_dir(extra).raw()])
```

## 后续可做（按性价比排序）

| 优先级 | 事项 | 说明与建议 | 大致工作量 |
| --- | --- | --- | --- |
| 高 | **技能触发测试** | 准备一批"该触发 / 不该触发"的问句，跑一遍看模型是否加载了正确的技能。`description` 写得对不对，只有测过才知道——这是这一层唯一的质量指标 | 半天 |
| 高 | **description 体检** | 加一个 `agent skills --lint`：检查描述过短、缺少触发场景、与别的技能描述高度相似（容易互相误触发） | 半天 |
| 中 | **多来源加载** | 支持"仓库技能 + 用户技能"分层，用户同名覆盖。团队协作时很有用 | 半天 |
| 中 | **技能内含资源** | 允许技能目录带附件（模板、示例文件），正文里用相对路径引用，由 `read_file` 读取 | 半天 |
| 低 | **版本与来源** | 给技能加 `version` / `source` 字段，便于追踪"这条流程是谁什么时候加的" | 两小时 |
| 低 | **远程技能** | 从 URL 或 git 仓库拉技能，概念上接近 Codex/Claude 的插件市场。功能诱人，但会引入信任与更新问题，建议等本地这套用顺了再说 | 两天起 |

我的建议：**先做"技能触发测试"**。技能的失败方式和工具完全不同——工具错了会报错，
技能错了是"模型压根没读它"，静默且难察觉。有了这批用例，你改 `description` 时
才有反馈信号。
